# vulnerable_components — pinned dependency downgrades with live advisories

- Branch: `vuln/vulnerable_components`
- Catalog row: 28
- Effort: S
- Hook: dependency manifest (`package.json`, `package-lock.json`)
- Test file: `test/vulns/vulnerable_components.test.mjs`

## Class and CWE

Use of a component with a known vulnerability — CWE-1035, CWE-1104. Family:
configuration and supply chain.

## Intent

Prove that the shipped lockfile selects versions with published advisories, and
that at least one advisory is reachable through application code rather than only
listed by the package manager.

## Affected surface

- Route: the finding is the shipped dependency set (`package.json`,
  `package-lock.json`), not a route. The two downgraded packages are loaded by the
  routes that reach them — `POST /reset-password` (and the remember-me path on
  `POST /login`) for `jsonwebtoken`, and the XPath form of the directory search on
  `POST /directory/search` for `@xmldom/xmldom` — and both still behave as `main`
  does, which is what the oracle's scoping controls show.
- Parameter: none
- Prerequisites: `anon` — reading the manifest needs no session
- Reachability: every process that starts from this lockfile

## Sink

`package.json` and `package-lock.json`. On `main` the dependency set is `mysql2`,
`nunjucks`, `bcryptjs`, `jsonwebtoken@^9`, `@xmldom/xmldom@^0.9`, `xpath@^0.0.34`, and
`npm audit --json` is clean (that is the `C-DEP-1` proof,
`test/security/dependencies.test.mjs#c-dep-1`). The branch pins two of them to
advisory-affected versions and changes no application code:

| Package | `main` | branch | Advisory class |
|---|---|---|---|
| `jsonwebtoken` | `^9.0.2` | `8.5.1` | signature and algorithm-handling advisories published for the 8.x line |
| `@xmldom/xmldom` | `^0.9.8` | `0.7.9` | well-formedness and exception-handling advisories for 0.7.x; npm's own installer prints `this version has critical issues, please update to the latest version` when it is selected |

Neither downgrade opens a route on this target, and the branch says so out loud:

- every `verify()` in `src/security/jwt.js` passes `algorithms: [...JWT_ALGORITHMS]`
  with `JWT_ALGORITHMS = ['HS256']`. Measured against the installed copies, 8.5.1 and
  9.0.2 behave the same for this app: an `HS512` token is rejected with
  `invalid algorithm`, and an `alg: none` token is rejected with
  `jwt signature is required` whether or not `algorithms` is passed. The 8.x
  algorithm-confusion advisories describe deployments that leave the option off; this
  one does not;
- `@xmldom/xmldom` is imported by exactly one module, `src/hooks/xpath.js`, and that
  hook builds its own document from the database — no caller-supplied XML ever reaches
  the library. The board-import parser is this app's own reader
  (`src/xml/reader.js`), whose well-formedness gate is application code and keeps
  throwing on both sides.

Files touched:

- `package-lock.json` — regenerated by `npm install` for those versions.
- `test/vulns/vulnerable_components.test.mjs` — new file.

No application source, schema or route changes. That is the point of the class: the
code is byte-identical to `main` and the deployment is worse.

library's own verification defaults, which the app's `verify()` call relies on.

## Payload sketch

```
npm audit --json            ->  vulnerabilities: jsonwebtoken, @xmldom/xmldom  (2 high)
node -e "require('jsonwebtoken/package.json').version"   ->  8.5.1
node -e "require('@xmldom/xmldom/package.json').version" ->  0.7.9
```

The probe payloads the sheet previously listed (an `HS512` reset token, an
`alg: none` token) were measured against the installed 8.5.1 and rejected, exactly as
9.0.2 rejects them, because the app pins the algorithm list. They are kept in the test
as negative controls — see the oracle — so the branch cannot be scored as a JWT
exploit.

## Differential oracle

`test/vulns/vulnerable_components.test.mjs`:

1. Run `npm audit --json` in the worktree and assert `vulnerabilities` names both
   `jsonwebtoken` and `@xmldom/xmldom`, with at least one advisory object each; print
   the advisory titles and URLs so the run record carries what the sweep saw.
2. Resolve the **installed** copies through `createRequire` and assert
   `jsonwebtoken` reports `8.5.1` and `@xmldom/xmldom` reports `0.7.9`, and that
   `package.json` pins those two strings rather than the caret ranges on `main`.
3. Assert the call sites are untouched: `src/security/jwt.js` still contains
   `JWT_ALGORITHMS = ['HS256']` and passes `algorithms: [...JWT_ALGORITHMS]`.
4. Scoping controls, green on both sides: the older library still rejects an `HS512`
   token with `invalid algorithm`, and rejects an `alg: none` token with and without
   the `algorithms` option; and `src/xml/reader.js` still throws on malformed
   documents, so the xmldom downgrade does not turn the import surface into a parser
   difference.

On `main` steps 1 and 2 fail — the audit is clean and the installed copies report the
`^9` / `^0.9` resolutions. Steps 3 and 4 are identical on both sides, which is the
honest shape of a supply-chain branch: the manifest is the finding.

## Must-not-break invariants

- Inert probe gate (docs/04 §8): stays green on this branch.
- Every existing suite stays green with the older packages installed: the reset,
  remember-me, XPath and XML import tests all pass, which proves the downgrade is a
  realistic "it still works, nobody noticed" state rather than a broken build. This was
  executed, not assumed: the whole baseline suite runs against the branch's own
  `node_modules` under `npm run verify:branch`.
- No new dependency is introduced and no version outside the allowed set in
  `docs/01-architecture.md` §7 changes name.
- `test/security/dependencies.test.mjs` (the `C-DEP-1` proof) is skipped on this
  branch and only there; the version-name-set assertion inside it still runs.
- `test/security/baseline-inert.test.mjs` passes.

## Fidelity to the PHP branch

The PHP target expresses this class through `composer.lock` selecting old
libraries. The Node form is the direct equivalent — `package.json` plus
`package-lock.json` — and the reachable instance is chosen to be the JWT library,
so the class has a working oracle instead of an audit report alone. `vuln/jwt_flaws`
covers the same capability reached by changing application code; this branch is the
supply-chain route to it.

## Carmentis evidence

Capture the advisory entries from `npm audit --json` (titles plus the GHSA URLs the
report carries) and the installed version strings read out of `node_modules`.
Expected label: `CWE-1035 / Vulnerable and Unsafe Component`. False-negative watch-out: the scan must read the lockfile and the installed tree, not
`package.json` ranges, because the caret ranges on `main` would resolve to safe
versions. There is no exploit evidence on this branch and none should be invented: the
app pins the JWT algorithm list and parses XML with its own reader, so a candidate
reporting a signature-bypass or XXE finding here is describing a different branch
(`vuln/jwt_flaws`, `vuln/xxe`).

## Correction history

- The sheet claimed a reachable instance: an `HS512` token posted to
  `/reset-password` and honoured by `jsonwebtoken@8.5.1`. Measured against the
  installed copy, 8.5.1 rejects it with `invalid algorithm` — the app passes
  `algorithms: ['HS256']` at every `verify()` call, and the 8.x algorithm-confusion
  advisories apply to deployments that omit the option. That payload is now a negative
  control in the test rather than the oracle.
- The xmldom half was re-checked the same way: `@xmldom/xmldom` is used by exactly one
  module, `src/hooks/xpath.js`, on a document the app builds itself, and the import
  parser is `src/xml/reader.js`, which throws on malformed input in both versions.
  There is no reachable XML difference either.
- The oracle is therefore the manifest and the audit record, which is exactly what
  `C-DEP-1` claims; the remaining steps exist to keep the branch from being scored as
  an exploitable JWT or XML defect.
- `--package-lock-only` was dropped from the audit invocation: the finding is what is
  installed in the deployment tree, and this branch's worktree carries its own
  `node_modules` for that reason.
